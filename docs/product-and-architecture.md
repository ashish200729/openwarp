# Product scope and architecture

OpenWarp is an independent, single-company deployment for administrators who manage employee records and colleagues who need a readable work directory. The landing page pairs a WebGL digit field with workspace screenshots captured with sample data. The workspace uses the same color tokens, mark and segmented meters with denser layouts for day-to-day work. The field draws one still frame when reduced motion is requested, stops offscreen, has a pause control, and is absent when WebGL2 is unavailable. The theme cookie holds only `light` or `dark`.

## Data and access

- Better Auth owns password hashing and database sessions. Administrators create accounts in the app with a one-time temporary password. The server redirects that account to the password page until it is replaced. An account can link to one employee record. Members see active employees and their own pay, time off, expenses and documents. A linked manager also decides time off and expenses for direct reports and doesn’t see their pay. Only administrators can view other employee statuses, run checklists, change records, record pay, run pay, export data, manage access, or see the activity log. Server entry points verify access, and writes recheck the role in their transaction. [Next.js authentication guide](https://nextjs.org/docs/app/guides/authentication), [Better Auth PostgreSQL adapter](https://better-auth.com/docs/adapters/postgresql)
- PostgreSQL enforces case-insensitive team name uniqueness, normalized unique employee emails, foreign keys, valid dates, and at most one open checklist per employee. A short transaction lock serializes administrative writes, including reporting checks and role changes. Version checks stop stale profile and team forms from silently overwriting new changes. The runtime role can append activity, pay history and job history and has no grant to rewrite or delete them. It can insert accounts and change roles, which in-app access management needs. Database operators retain administrative access. [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [locking](https://www.postgresql.org/docs/17/explicit-locking.html)
- Adding someone can start onboarding or create an active profile. Onboarding completion activates the employee. Cancelling onboarding archives the profile. Starting offboarding requires a last day. Completing offboarding requires every task and reassignment of direct reports. Cancelling offboarding returns the employee to active status. Archived profiles retain their history and can start a new onboarding checklist for a rehire.
- New checklists copy the task template into durable rows. Checklist actions track human work outside OpenWarp. No third-party action runs when a task is completed. Primary employee edits, workflow changes and their history entries commit together.
- Next.js Server Components render private pages from the server. Client JavaScript handles form pending states, account actions and active navigation. Employees can browse the directory as responsive cards or a wider table. Color is paired with labels, and data meters have names and numeric values. [WCAG reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow)
- Money is stored as integer cents in one company currency, which locks once pay, expenses or pay runs exist. A pay run uses each person’s latest rate on the period’s end date, prorates salaries by weekday, claims approved expenses so two runs can’t reimburse the same one, and refuses overlapping periods. Approved runs are read-only. Approval checks that the run hasn’t changed since it was reviewed.
- Time off counts weekdays minus company holidays and holds pending requests against the annual allowance. The shared calendar shows that someone is away and withholds the type and note.
- Uploads are limited to 5 MB and to PDF, PNG and JPEG, identified by file signature. Files are stored in PostgreSQL, always download, and are served with a sandboxing policy. Each download rechecks access.
- Completing an offboarding checklist archives the profile, disables its linked account and ends its sessions.
- Pay items are stored per line, so an approved run reproduces exactly and the database refuses changes to it. Corrections are opposite runs. Approval recalculates and refuses a draft that no longer matches its sources. Each schedule period allows one regular run that hasn’t been reversed.
- Bank details, identity numbers, dates of birth, addresses, dependents, webhook secrets and two-factor secrets are sealed with AES-256-GCM, bound to their record. API tokens and backup codes are stored as keyed hashes.
- A password sign-in with two-factor enabled opens nothing until the second factor passes. Single sign-on binds an issuer and subject to an existing account on first use.
- API tokens act for the administrator who created them and stop working when that person loses the role. Pay and personal data need explicit scopes.
- One in-process worker, guarded by a database lock, sends email, webhooks, reminders and routines. Webhooks resolve the destination and refuse private addresses at delivery.

## Getting started and invitations

Warp’s entry screen distinguishes people joining an employer from people setting up a company. Its public HRIS guide describes a worker receiving an invitation and completing personal details, documents and pay information through self-service. Its admin guide documents role assignment at invitation time, expiry, replacement and revocation. These public descriptions and the supplied entry-screen reference informed OpenWarp’s flow. [Warp HRIS](https://www.warp.co/hris) · [Warp roles and invitations](https://help.joinwarp.com/articles/8668824598-roles-and-permissions-in-warp)

Warp offers employers a guided session when they move payroll from another provider. Its contractor product starts with an invitation and collects the details needed to pay that worker. OpenWarp uses the same distinction to decide what to ask first. Employers can start with company settings before they have hires. Workers see their assigned team before choosing a password, and their own record determines which onboarding tasks they receive. [Warp employer onboarding](https://www.warp.co/onboarding) · [Warp contractor onboarding](https://www.warp.co/global-contractors)

OpenWarp hosts one company per installation. **Join my team** opens a personal invitation from that installation. The employee record determines team membership. **Set up my company** takes an authorized administrator to currency and pay schedule settings, employee creation and account access. A new employer can follow the self-hosting guide. Returning users can go straight to sign-in.

In **Settings → Access**, create a linked account, expand its row, and create a private invitation link. The same seven-day, single-use credential works through email or private sharing. A replacement invalidates the previous invitation, including any copy already sent by email. Revocation applies to the specific invitation the administrator reviewed. A password recovery request can coexist with an invitation. Choosing a new password consumes both links and ends existing sessions. The recipient chooses a password, signs in, completes any required second factor, and reaches their own onboarding tasks if their employee record is onboarding. SSO-only accounts use their configured identity provider. Link delivery and password recovery use random tokens, stored as hashes, and the configured workspace origin. [OWASP token and recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
